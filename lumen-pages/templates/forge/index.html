What a rehearsal actually does

Three steps, always in this order. Each one can fail the plan, and a failed plan cannot be shipped without --i-read-the-report.

1

Snapshot

Forge copies the schema, indexes, constraints and a sampled slice of rows from each table into a local engine of the same version. Sampling keeps the biggest tables honest without pulling terabytes.

forge snapshot --sample 50k
schema      41 tables, 118 indexes
rows        orders 50k of 31M · events 50k of 410M
engine      postgres 16.3 (matches prod)
2

Rehearse

The migration runs against the snapshot with a stopwatch on every lock. Forge reads the engine's execution plan to catch table rewrites, full index builds without CONCURRENTLY, and defaults that touch every row.

forge plan 0042_orders_fulfilled_at
lock        AccessExclusive on orders  0.3 s
rewrite     none (nullable, no default)
rollback    replayed · schema hash matches
3

Gate and ship

Before touching an environment, Forge hashes its live schema and compares it with the snapshot. Drift stops the ship. Otherwise it applies to each environment in the order you declared, waiting for your health check between them.

forge ship --to staging,prod
staging     hash ok · applied 0.4 s · health 200
prod        hash ok · applied 0.6 s
report      forge.sh/r/8f21c (kept 90 days)
